# Policy operation evidence and boot recovery

**Status: private NAS codecs/comparison and initial read-only collector exist; writer and
product admission remain proposed and unqualified.**
The current Store, OwnedStore and read-only BootstrapAuthority remain unchanged.
This design is a contributor handoff, not a migration or installation procedure.

## Problem and existing boundaries

`Store.Commit` checks the expected revision, writes/syncs/closes the candidate,
renames it to current and syncs the directory. Publication errors can leave new
current bytes even when the caller receives an error. A process may also exit
after the local commit and before sending a response. Reopening valid bytes is
therefore not evidence that the original caller received success.

`OpenWithCodec` syncs current and the directory when reopening. This establishes
a new synchronization boundary, not the outcome of the original operation.
`OpenOwnedWithCodec` assumes separately provisioned initialized state. It does
not implement product bootstrap, reconcile pending operations or identify an
earlier Owner whose review state was lost at process exit.

The existing retained bootstrap observer intentionally does not sync, initialize,
remove evidence, transfer ownership or issue policy leases. Its read-only
classification must remain usable independently of any future writer.

Native account and Samba journals already have distinct intent/confirmation
transitions. Reuse their vocabulary and strict decoding pattern; do not combine
their credentials, effects or independent revisions into this policy journal.

## Facts that must not be conflated

| Evidence | What it can establish | What it cannot establish |
| --- | --- | --- |
| Valid current policy | Schema-valid bytes and positive revision at observation | Provisioning, prior fsync success, origin or client acknowledgement |
| Matching intent | A declared operation and expected before/after policy | Publication or absence of side effects |
| Matching local receipt | Recorded local confirmation for that exact operation | Response delivery, service activation or absence of external users |
| Surviving files after restart | Evidence present on the observed medium now | The previous syscall return values or tested power-loss behavior |
| Retained lock/watch | One cooperating authority's current lifetime | Durable quarantine, protection against root, physical durability or anti-rollback |

A hash binds bytes; it is not authentication. Root-owned local evidence needs
trusted provisioning and parents, cooperating writers and a qualified medium.
Without a separately designed rollback-resistant anchor, restoring an old
complete state bundle cannot be distinguished reliably from legitimate history.

## First implementation: private NAS-only evidence matching

The [internal NAS comparator](../naspolicyevidence/README.md) implements the first pure slice.
Inputs are trusted in-process observations, never HTTP-supplied permissions.
This slice has no file opener, writer, synchronization, recovery, consumer or
Owner constructor. Its result is diagnostic data, never a capability.

Both records use a versioned format and reject unknown/duplicate/non-exact keys,
null, trailing documents, invalid UTF-8, excess nesting and excess input using
the existing `internal/configjson` envelope. Proposed maximum: 4 KiB per record,
depth 2; one flat record, no history arrays or unbounded strings. Return fixed
errors without raw fields, document contents or underlying I/O messages.

Proposed immutable operation tuple:

| Field | Constraint / purpose |
| --- | --- |
| `format`, `schema_version` | Distinct intent/receipt format tags; schema 1 only |
| `installation_id` | Nonzero 128-bit opaque ID, canonical lowercase hex; separately provisioned, not a bay/path/MAC/serial |
| `operation_id` | Nonzero 128-bit opaque ID, canonical lowercase hex; locally generated by a future trusted coordinator |
| `base_revision` | Positive initialized revision; first enrollment is a different operation |
| `next_revision` | Exactly base + 1; refuse overflow |
| `base_sha256` | Canonical lowercase digest of exact bounded previously confirmed policy bytes |
| `next_sha256` | Canonical lowercase digest of exact bounded candidate policy bytes |

The receipt repeats the entire tuple and a fixed `local-confirmed` phase.
Do not include passwords, password-derived hashes, CHAP values, keys, raw command
output, arbitrary paths, transport acknowledgements or a fabricated timestamp.
The NAS policy contains references, not the secret values themselves; extending
this design to secret-bearing documents needs a separate confidentiality review.
IDs/digests remain private and are not returned in management HTTP diagnostics.

Proposed matcher observations, always read-only:

| Observed evidence | Diagnostic result | Permitted action in this slice |
| --- | --- | --- |
| No operation evidence | No recorded operation | None; not pristine, initialized or boot-authorized |
| Intent only; current equals expected base | Unconfirmed operation, base observed | None; missing receipt is not replay permission |
| Intent only; current equals candidate | Publication observed without confirmation | None; preserve evidence and require review |
| Exact intent + receipt + candidate current | Matching local confirmation records | None; not admission or client acknowledgement |
| Orphan receipt, tuple mismatch, foreign installation, unrelated current | Inconsistent evidence | None; require review |
| Missing/partial/unavailable policy observation | Unavailable/incomplete evidence | None; no partial positive result |

The matcher validates the policy with the fixed trusted codec as well as its
revision/digest. It must not accept an arbitrary caller-provided digest as proof
of a file read. A later collector supplies complete, bounded, retained-origin
observations; the pure matcher itself cannot establish that provenance.
When one role is ambiguous, return no usable match. Retain the existing separate
invalid/unsupported diagnostic rather than inventing an automatic migration.

## Adopted writer retention and initial publication primitive

Retain current, the previous exact base and the latest operation records only.
A new explicitly authorized operation may rotate a verified completed set;
unknown, partial or pending evidence is preserved. Low space refuses rather
than deleting history. Keep the six fixed roles and stage through the exclusive
pending name. This is the adopted internal host/disposable-QEMU direction,
not product provisioning, reconciliation, boot admission or physical placement.

The private `stageNASEvidenceRole` implements one fixed-role write/sync/close/
rename/directory-sync/exact-readback step. It never removes pending evidence,
rewrites the header or resets a watch. A retained coordinator must still validate
policy transitions (including NFS bindings), authorize replacements, account for
its own events and preserve review across all stages. The complete ordered
base/intent/prior-receipt retirement/current/receipt transaction is not wired.
The pure NAS `EncodeOperation` prepares bounded metadata using the strict
existing records, exact policy hashes/revisions and retained NFS source checks.
Prepared receipt bytes are not confirmation: ID allocation/reuse checks and
the publication order remain obligations of that future retained coordinator.

The private writer event fence checks bounded complete inotify records after a
known stage: pending create/modify/close and a cookie-paired rename, or retirement
of the previous receipt. Missing, extra, malformed, foreign-watch and watch-loss
events refuse. Rename pairs can span reads and MODIFY events may coalesce.
It neither opens an authority nor clears review. The future coordinator still
must retain its original directory/lock and verify every expected object and
byte; a matching event sequence cannot identify the writer or authorize admission.

The shared collector can return a private complete set of bytes and file stamps;
any collection error returns an empty set. Pending remains metadata-only. The
existing diagnostic facade is unchanged; the caller must still guard the original
root/watch before consuming this candidate set. It is not writer authority.

## Follow-up coordinator: requirements, not an implementation

Do not bolt receipt writes onto the existing two-name policy directory: its
bootstrap census intentionally treats unknown entries as evidence. Define a
separate explicit schema and bounded namespace before adding new file roles.
Do not assume that two directories or files publish atomically as one bundle.

The future coordinator must:

1. Retain one trusted state-root identity and exclusive single-writer authority
   across classification, operation, publication and any authorized admission.
   Do not close the bootstrap observer and reacquire a path to admit an Owner.
2. Require a separately confirmed base, no active consumers and no unresolved
   operation. Allocate the operation ID internally. Reject stale inputs before
   effects; never select a namespace or backend from an HTTP request.
3. Persist intent, exact base evidence and candidate binding before attempting
   policy publication. Failed intent durability forbids the publication attempt.
   Keeping only the old digest is insufficient for restoring the previous bytes.
4. Perform the existing bounded policy transaction once. Any attempted uncertain
   I/O or in-flight cancellation remains review; never repeat the operation to
   discover whether it succeeded.
5. Reobserve the exact candidate under retained authority. Record local receipt
   only after successful local publication/readback and qualified synchronization.
   A failed or interrupted receipt leaves the operation unresolved even if the
   policy looks correct. Do not pretend a receipt proves the final sync returned.
6. Return a locally verified outcome only after all required boundaries. HTTP
   delivery is a separate outcome; a lost reply must remain distinguishable.
7. Preserve intent/base/receipt and bounded recovery evidence until explicit
   retention/reconciliation rules allow cleanup. No automatic pending deletion,
   old-state promotion, rollback, conversion or service restart.

The terminal receipt write itself can be interrupted. Recovery must inspect
the retained evidence under the qualified filesystem's documented guarantees;
record presence alone does not certify a historical successful return value.
An explicit reconciliation may establish a new confirmed epoch, but requires
fresh state/consumer observations and a separately specified authorized action.

## State-bundle and boot prerequisites

Policy evidence is only one role. Product admission must also account for admin
credentials, installation identity, volume registry, native account ledger and
journals, Samba private state, CHAP secret references and system/network settings.
Do not fsync all stores to manufacture pristine or confirmed status. Partial
provisioning, missing roles and unknown schema versions cannot enroll or enable.

Existing role owners remain the sole mutators. A state-root coordinator may
compose them in a fixed lock order, but cannot infer their individual external
side effects from a shared policy revision. Outstanding identity/session/mount/
backing use must fence reconciliation and admission. Prior volatile review is
not cured by opening a new process; durable review/operation evidence needs its
own recovery policy and failure handling when it cannot be written.

Physical placement, wear, capacity, filesystem features, medium identity, NAND/
ECC/bad blocks and recovery remain M7/M10 gates. This design neither selects
the legacy configuration partition nor prescribes EX4 writes.

## Work packets and acceptance tests

| Packet | Deliverable | Acceptance / refusal cases |
| --- | --- | --- |
| M1.3b.1 | Approved record schema and pure matcher | One real before/after nonempty NAS policy pair; all record/policy bindings checked; no filesystem or activation imports |
| M1.3b.2 | Strict codecs and diagnostics | Bounds, duplicate/unknown/null/UTF-8/trailing/version refusals; zero results on error; no IDs/digests in public diagnostics |
| M1.3b.3 | Read-only retained evidence collector | Complete fixed-role census; no-follow/same-medium/permissions/single links; cancellation/drift/overflow/close faults retain review; no reopen gap |
| M1.3c | Explicit writer protocol on disposable media | Intent-before-effects, preserved base, exact readback/receipt; every write/sync/rename/close/return boundary interrupted; no retry/admission on uncertainty |
| M1.3d | Authorized reconciliation | Fresh complete role/consumer state; stale/concurrent requests refuse; original evidence preserved; process restart cannot clear unresolved work |
| M1.2c | Product bootstrap/state-bundle coordinator | Distinguish unprovisioned/partial/confirmed/review/corrupt/incompatible/unavailable; no automatic adoption; retain authority into admission |

For b.1/b.2, begin with fast no-Docker host tests, then pinned Linux vet/unit/race
and a bounded actual ARMv5 run in the existing optional fixture. Cross-compilation
is not execution. Do not add another default historical build stage.
For later writer tests, reuse disposable 32-MiB ext4 media and existing full/RO/
SIGKILL controls; preserve all old assertions, bounds and auto-removed containers.
Process interruption is not sudden power loss or failing EX4 NAND qualification.

## Decisions still required

- Product state I/O needs admission beyond the adopted NAS evidence namespace.
- Choose the state-root/bundle namespace and atomic publication strategy; a
  generation/manifest design is an option, not a silently selected format.
- Specify what can authorize reconciliation after receipt-publication uncertainty,
  and how durable review survives inability to persist another record.
- Qualify the adopted latest-operation retention and low-space refusal behavior.
- Define installation provisioning/replacement and anti-rollback expectations;
  opaque random IDs alone do not solve ownership, cloning or rollback.
